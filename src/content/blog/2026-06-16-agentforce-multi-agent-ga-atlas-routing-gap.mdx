Something changed yesterday.

[Salesforce's Summer '26 release went live on June 15](https://www.salesforce.com/news/stories/summer-2026-product-release-announcement/), and the headline feature is not incremental: multi-agent orchestration graduated from beta to general availability. Atlas Reasoning Engine 3.0 ships as the underlying coordination layer. [Agentforce annual recurring revenue hit $800 million](https://enterprisedna.co/resources/news/salesforce-summer-26-agentforce-800m-arr-multi-agent-2026/), up 169% year over year. Multi-agent AI at enterprise scale is no longer an architectural experiment. As of yesterday, it's a production GA release running inside one of the largest enterprise software deployments in the world.

That's worth pausing on. Multi-agent orchestration going GA at Salesforce isn't a startup announcement or a cloud platform update. It's the moment the architecture becomes default for enterprises that have spent a generation standardizing on Salesforce infrastructure.

And there's a gap at the center of it that the release notes don't address.

## How Atlas 3.0 Actually Makes Routing Decisions

The core capability is straightforward: [one orchestrator agent receives a request, inspects which specialist agents are registered, reads their descriptions and available actions, and routes the work to whichever specialist is best suited](https://chatforest.com/builders-log/salesforce-summer-26-agentforce-multi-agent-orchestration-atlas-a2a-mcp-builder-guide/). A2A protocol handles cross-cloud communication — if you have a procurement agent on Azure and a CRM agent in Agentforce, they can coordinate through a standardized message layer. MCP handles the data access layer. Atlas 3.0 is the reasoning engine that reads the agent registry and decides who handles what.

This is real infrastructure. [The engineering is serious](https://engineering.salesforce.com/how-agentforce-delivers-trusted-extensible-ai-agents-for-enterprise-orchestration/). The coordination pattern — orchestrator with specialist subagents, shared context across channels, user doesn't repeat themselves — solves a genuine enterprise problem. Before multi-agent orchestration, the alternative was either monolithic agents trying to handle everything or end-users manually navigating between specialized tools. The architecture Salesforce shipped yesterday is the right one for complex enterprise workflows.

The problem isn't the architecture. The problem is what the orchestrator routes on.

## The Routing Decision Is a Trust Decision

When Atlas 3.0 reads a specialist agent's description and decides to route a billing escalation there, it's making a trust decision. It's deciding: this agent can handle this task.

The decision is based on what the agent's description says. That's it.

An agent card declares capabilities. It says the agent handles billing escalations, claims it can access the right systems, lists its available actions. Atlas reads the declaration and routes accordingly. What the declaration cannot contain is performance history: how this agent has actually performed on billing escalations in the past, where it fails, what input distributions cause it to degrade, whether it's had a model update that shifted its behavior in edge cases.

[This is what practitioners are calling the seam problem](https://www.siroccogroup.com/agentforce-multi-agent-the-seam-problem/). The seam between orchestrator and specialist is where failures propagate and where trust needs to be established — and right now, the trust model at that seam is declarative, not evidential. The orchestrator trusts the description. It has nothing else to trust.

In a single-agent deployment, this is a manageable gap. You deploy one agent, evaluate it, monitor it, discover its failure modes, and iterate. The feedback loop is tight. In a multi-agent pipeline, the gap compounds. The orchestrator routes work based on declarations, the specialist executes, and the orchestrator accepts the output and incorporates it into the next delegation. If the specialist is operating at 70% reliability on the task distribution being routed to it, the orchestrator doesn't know. It reads the next request, routes again, and the downstream agent acts on output that was wrong 30% of the time.

[Enterprise AI research consistently documents a 37% gap between benchmark performance and real production performance](https://www.salesforce.com/agentforce/multi-agent-orchestration/) across enterprise deployments. In a single-agent system, that gap surfaces as inconsistent output. In a chained multi-agent system, it compounds across every delegation hop. An orchestrator routing on declarations rather than performance data is assembling a pipeline from components whose actual reliability is unknown.

## What Changes When Multi-Agent Goes Enterprise-Default

The reason this matters more at Salesforce scale than anywhere else is the distribution.

When a cloud platform ships multi-agent orchestration as a generally available feature, the typical adopter is a sophisticated enterprise team with dedicated AI engineering capacity. They're thinking about agent reliability. They're asking the right questions. They're stress-testing their pipeline before it handles production workloads.

When Salesforce ships multi-agent orchestration as a generally available feature to its existing customer base, the typical adopter is an enterprise that already runs its CRM, sales automation, and customer operations on Salesforce infrastructure — and now gets multi-agent capability as part of the platform they already bought. These teams have real business workflows to automate and real deadlines. They are not, in most cases, doing systematic pre-deployment evaluation of specialist agent reliability on their specific task distribution before assembling the pipeline.

[At $800M ARR and 169% year-over-year growth](https://enterprisedna.co/resources/news/salesforce-summer-26-agentforce-800m-arr-multi-agent-2026/), Agentforce is moving fast across enterprise customers who didn't build their careers around LLM evaluation methodology. The routing decisions Atlas 3.0 makes in those deployments will default to trusting descriptions because that's all the orchestrator has to route on.

## The Infrastructure Layer That Doesn't Exist Yet

Atlas 3.0 is impressive work. The A2A and MCP layers are the right protocols for multi-agent communication. The architectural pattern Salesforce has shipped is sound.

What doesn't exist yet is the layer that tells the orchestrator something about how the specialist agents it's routing to have actually performed — not what they claim to do, but what they demonstrably do across the task distribution being delegated to them. Governance infrastructure tells you whether agents operate within declared policy. Communication protocols tell you whether agents can coordinate. Neither tells you whether the specialist agent you're routing a critical workflow to is actually reliable on that workflow.

The routing layer needs to make decisions based on evidence, not declarations. That means specialist agents in a production multi-agent system need a performance record that's legible to the orchestrator — or to the team assembling the pipeline before the orchestrator is asked to route anything real. What did this agent actually do on billing escalations like this one? Where does it fail? How does it perform relative to alternative agents on the same task class?

Without that layer, multi-agent orchestration is powerful coordination infrastructure assembled from components with unknown reliability characteristics. The seam between orchestrator and specialist — the gap Atlas 3.0 bridges with routing logic — is where trust either exists as infrastructure or gets substituted with hope.

The agents are talking to each other. Someone still needs to verify they're worth listening to.
