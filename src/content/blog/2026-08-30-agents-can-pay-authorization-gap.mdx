An AI agent just spent your money. Can anyone prove you said it could?

That's the question [Fortune raised this week](https://fortune.com/2026/08/24/google-ai-agent-payment-protocol-gap/) examining Google's Agent Payment Protocol — the infrastructure that lets AI agents initiate and complete financial transactions autonomously. AP2 is technically coherent. Agents can be provisioned with payment credentials, execute purchases, book services, and close contracts without a human approving each step. That capability is exactly what enterprise buyers have been asking for: agents that don't pause at every transaction to wait for a human to click "confirm."

The problem [The Conversation documented in the same week](https://theconversation.com/an-ai-agent-spent-your-money-can-anyone-prove-you-authorized-it-288485) is that capability and authorization are two different things, and right now the industry has built most of the former while leaving most of the latter to faith. Agents can execute payments. What's missing is a reliable, verifiable record proving that a human authorized that specific class of action, that specific delegation scope, and that specific agent to carry it out.

This isn't a hypothetical edge case. It's the structural gap at the center of agentic commerce — and it's about to collide with the law.

## The Delegation Problem

Here's the distinction that matters. An agent being capable of paying is a technical property. An agent being authorized to pay — in a way you can prove to a court, an auditor, or a counterparty who disputes the transaction — is an entirely different requirement.

Current agent deployment architectures handle authorization the same way early OAuth implementations handled permissions: by treating broad, upfront consent as equivalent to specific, informed delegation. The user installs the agent. The agent has payment access. The agent pays. That chain of events looks like authorization only if you ignore the gap between "the user set up the system" and "the user specifically intended this agent to make this purchase at this time under these conditions."

The legal and compliance implications are immediate. A transaction an agent executes without a verifiable delegation trail is a transaction with contested provenance. In a dispute — a fraudulent charge, a compliance audit, a vendor claiming the payment never came — the question "can you prove a human authorized this?" becomes determinative. If your audit log records what the agent did but not what the user actually delegated, you're producing evidence that confirms the action and says nothing about the authorization.

## Washington Noticed

Senator Mark Warner introduced the [AI AGENT Act (S. 5051)](https://www.congress.gov/bill/119th-congress/senate-bill/5051) on July 21, 2026 — a bill that directs NIST to develop technical standards specifically for verifying human delegation to AI agents and maintaining auditable action records. The bill is narrow by design. It doesn't try to regulate AI generally or define what agents can and can't do. It focuses on the authorization problem: how do you prove, after the fact, that a human actually delegated a specific action to a specific agent?

That framing reflects an accurate diagnosis. The problem isn't that agents can act autonomously — that's the whole point. The problem is that autonomous action without verifiable delegation is legally indistinguishable from unauthorized action after the fact.

NIST's own standards initiative, currently reviewing public comments on a February 2026 draft, is working toward the same target: adapting OAuth 2.0/2.1, OIDC, and SPIFFE/SPIRE — protocols originally built for software services, not autonomous agents — to handle agent identity and delegation chains. The technical challenge is real. Human users don't issue tokens to agents the way developers configure service accounts. The delegation is often implicit, behavioral, and context-dependent in ways that don't map cleanly to existing identity primitives.

The agency is trying to retrofit authorization standards designed for static service-to-service calls onto systems that make contextual decisions in real time. That's harder than it sounds, and the draft acknowledges it.

## The Interoperability Standards Gap

This week's [consolidation of the A2A and MCP protocols under the Agentic AI Foundation](https://www.axios.com/2026/08/17/a2a-agentic-ai-foundation-open-ai-standards) — a neutral Linux Foundation-governed body with 250+ members including AWS, Anthropic, Google, Microsoft, and OpenAI — is a genuine coordination milestone. Having a two-protocol stack (MCP for tools and context, A2A for agent-to-agent coordination) under shared governance reduces fragmentation risk.

But here's the problem: neither protocol solves authorization provenance. A2A specifies how agents communicate and coordinate. MCP specifies how agents access tools and context. [A governance gap paper published this month](https://arxiv.org/pdf/2606.31498) maps what neither protocol can currently express: fine-grained authorization chains, audit provenance that survives agent handoffs, consent revocation across multi-agent pipelines, and cross-jurisdictional compliance evidence.

When Agent A delegates a payment task to Agent B in an A2A pipeline, the authorization chain — who originally approved this class of action, under what constraints, for what duration — is not carried in the protocol. It exists, or doesn't exist, in whatever the deploying organization built around the agents. Most organizations haven't built it.

A two-protocol stack for agent connectivity is a foundation. It's not a trust stack.

## What Comes Next

The NIST standards work and the AI AGENT Act are both pointed at the same primitive: agent authorization should produce a verifiable artifact, something that travels with the action and establishes delegation provenance in a form that survives a dispute. That artifact needs to capture what the human actually authorized — not what the agent is technically capable of doing, not what the system was configured to allow, but the specific scope of delegation the human intended.

Building that verifiably is harder than building the payment capability itself. It requires knowing what agents are running, what scope they've been granted, and whether each action falls within that scope — evaluated at the time of action, not reconstructed from system logs after the fact. It also requires that verification to be legible to parties outside your organization: auditors, counterparties, regulators.

In the near term, the practical response for any enterprise deploying agents with write access to financial systems is the same logic that applies to agents making consequential decisions in regulated sectors: don't run autonomously against production without a structured authorization trail. If you can't produce, from your own infrastructure, a verifiable record of what was delegated and by whom, human review before execution isn't overcaution — it's the only defensible position.

The authorization gap is the next infrastructure problem in agentic deployment. The payment protocols got built first because payment is the use case everyone can see the value of. The verification primitives are being built now, in public, under genuine pressure from regulators who've realized that "the agent did it" is not an authorization record.

Agents can pay. Proving you authorized it — in a way that holds up — is still the hard part.
