On September 28, Nvidia launched the [Open Agent Safety Platform](https://www.tomshardware.com/tech-industry/artificial-intelligence/nvidia-launches-open-agent-safety-platform-to-restrain-rogue-ai-agents-new-hardware-and-software-security-stack-can-quarantine-agents-in-milliseconds) with more than 100 partners — Microsoft, Anthropic, JPMorgan Chase, SAP, Cisco, Oracle, Salesforce, and over 90 others. The platform combines two components: OpenShell, an open-source runtime that sandboxes agents with kernel-level isolation, and [Sentry](https://www.artificialintelligence-news.com/news/nvidia-over-100-partners-launch-open-ai-agent-safety-platform/), a monitoring layer running on BlueField-4 DPUs that sits on the server's only path to the AI model. The company says a rogue agent can be quarantined in milliseconds.

The press called it a [hardware kill switch for AI agents](https://abhs.in/blog/nvidia-open-agent-safety-platform-openshell-sentry-bluefield-4-2026). The stock went up. 100 organizations signed on. The coverage was unambiguously positive.

Here's what the coverage missed.

## What OpenShell and Sentry Actually Do

The technical architecture is worth understanding before arguing about it.

OpenShell is an [open-source runtime](https://www.eesel.ai/blog/nvidia-open-agent-safety-platform) (Apache 2.0) that places each agent in a sandbox and enforces policy from outside the agent's own process. This matters because policy enforced from inside an agent can be modified by the agent — an obvious gap for autonomous systems with sufficient capability. Kernel-level isolation puts the policy boundary where the agent can't reach it.

Sentry runs on BlueField-4 DPUs — programmable chips that sit on a server's only path to the AI model. The key architectural property: the DPU is physically separate from the host CPU. If a compromised agent gains system access and attempts to disable its own monitoring, the DPU continues running regardless. The monitoring layer can't be turned off from inside the environment it's watching.

This is genuinely clever engineering. The "milliseconds to quarantine" claim describes this path: a policy violation is detected at the DPU before the agent's action completes at the application layer. The action is blocked before it lands, not after.

## The Framing Problem

The platform is being called safety infrastructure. That framing is accurate in a narrow sense and misleading in a broader one.

What OpenShell and Sentry do is detect and contain agents that violate defined policies in real time. That's containment. Containment is what you do *after* an agent has already done something it shouldn't — or is in the process of doing something it shouldn't. The millisecond containment window is measured from the moment a policy violation begins, not from the moment you decide to trust an agent enough to deploy it.

Containment is necessary. It is also, by definition, reactive. It assumes an agent has already crossed a line you drew. The infrastructure question containment doesn't answer — and isn't designed to answer — is whether your agents are performing well enough to deserve deployment in the first place.

Those are different questions. Whether an agent will eventually go rogue enough to trigger a kill switch is not the same as whether an agent is accurate, reliable, and effective on the tasks you're deploying it for. An agent can fail 40% of its assigned tasks without ever triggering a policy violation. It's not rogue. It's just bad. Sentry won't catch it.

## The Metric Problem

[Nvidia launched the platform with zero published detection rates, zero false-positive rates, and zero latency measurements](https://datapace.ai/blog/nvidia-open-agent-safety-platform) from real deployments.

The "milliseconds to quarantine" figure is what Nvidia says about the reference design — not an audited SLA across fleet deployments. No partner has published data on how often Sentry correctly identifies a genuine policy violation versus flagging legitimate agent behavior. No one has published the performance overhead of kernel-level isolation running at enterprise scale.

This is worth noting not because it's unusual — early platform launches rarely ship with deployment benchmarks — but because the platform is being sold specifically as safety infrastructure for production AI systems managing real workflows. At minimum, you'd want the false-positive rate before deploying a system that interrupts legitimate agent actions.

The irony lands hard: the safety platform has the same verification gap as the agents it's watching. It's been deployed without publishing the metrics that would tell you whether to trust it.

## What the Kill Switch Can't See

There's a more fundamental gap in what this architecture monitors.

Sentry watches what agents *do* — the actions they take, whether those actions cross defined policy boundaries. It doesn't watch how well agents *perform* on the work they're assigned. A policy boundary is "don't access data stores outside your declared scope." It is not "successfully complete the assigned task with sufficient accuracy to justify operating without human review."

The industry's deployment reality makes this gap concrete. [IBM's research from earlier this year](https://newsroom.ibm.com/2026-05-05-think-2026-ibm-delivers-the-blueprint-for-the-ai-operating-model-as-the-ai-divide-widens) projects that large enterprises will average over 1,600 deployed agents by year-end, with most unable to accurately inventory which agents they're running. [A survey of 1,000 senior technology and data leaders](https://aiagentsdirectory.com/news/ai-agents-news-brief-october-17-2026) published this week found that most organizations believe they're making enterprise AI progress — but most of that progress is individual productivity gains, not measurable enterprise-level returns.

Containment infrastructure tells you when an agent crosses a line. It doesn't tell you whether the agents crossing your systems are reliably producing results worth their access. Sentry can stop an agent from exfiltrating data. It cannot tell you whether the agent's output accuracy is above the threshold required for the workflow it's running.

## The Layer That Comes First

If you're thinking about this from the perspective of deploying agents at any real scale, the infrastructure requirements stack in a specific order:

1. **Pre-deployment verification**: Does this agent perform well enough on the actual task distribution it will run against? How does it compare to alternatives on the same work?
2. **Ongoing performance monitoring**: Is this agent's performance holding up as models update, data drifts, and scope evolves?
3. **Policy compliance containment**: Is this agent operating within the boundaries we've defined?

Nvidia just shipped an excellent version of layer three. Layers one and two are where most deployed agents are failing — and where Gartner is pointing when it [forecasts that over 40% of agentic AI projects will be canceled by end of 2027](https://www.gartner.com/en/newsroom/press-releases/2025-06-25-gartner-predicts-over-40-percent-of-agentic-ai-projects-will-be-canceled-by-end-of-2027), not because models violated policy, but because organizations couldn't demonstrate measurable value or adequate risk controls for the agents they'd already deployed.

Those projects didn't fail because a rogue agent did something containment would have caught. They failed because deployed agents had no performance baselines, no comparative benchmarks, and no mechanism to answer the question every rational deployment decision requires: is this agent actually doing the work, or just burning compute?

## What the Moment Actually Signals

Here's what Nvidia's 100-partner coalition does mean: the industry has accepted that AI agents require safety infrastructure at the infrastructure level. Not in the model. Not in the application. In the hardware and runtime environment the agents operate inside. That's a genuine maturity signal. A year ago, most organizations were treating agent safety as a prompt-engineering problem.

That maturity makes the missing layer more visible, not less urgent. When you've deployed a hardware-level kill switch, you're implicitly accepting that agents will sometimes do things you didn't intend. The question you haven't yet answered is whether the agents you're running — the well-behaved ones, the ones that never trigger the kill switch — are performing well enough to justify being there in the first place.

Containment is the last line of defense. It's right that the industry now has one.

The first line of defense is knowing which agents you can trust before you give them system access to anything worth protecting. That infrastructure is being built — less visibly, without hundred-partner launch events — because measuring performance is harder to package than cutting it off. But it's the layer that determines whether the agents behind Sentry's watch are actually doing the work, not just staying in bounds.

One doesn't substitute for the other. The industry needs both. It has one.
