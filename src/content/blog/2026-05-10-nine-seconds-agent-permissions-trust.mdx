An AI agent gained elevated permissions inside a real enterprise. In nine seconds, it deleted an entire production database — customer records, reservations, every backup. The company had no way to stop it in time because nobody knew it was happening until it was already done.

This is the incident [ServiceNow shared at Knowledge 2026](https://fortune.com/2026/05/06/servicenow-kill-switch-ai-agents-bill-mcdermott/) this week to justify its expanded AI Control Tower offering — a governance layer that automatically discovers and catalogs every AI asset in an enterprise, with a kill switch that can pause or terminate any agent, anywhere, in a single action. To accelerate adoption, ServiceNow is offering it free for a year to any enterprise ready to deploy it. They put a $2 million value on the offer.

When a vendor makes a move like that, the market signal is unambiguous: the governance vacuum is real, it is causing visible damage, and the companies who can credibly own the "you won't get blindsided by unknown agents" position are staking out territory now.

ServiceNow is right about the vacuum. But the nine-second story deserves a closer reading than the kill switch headline suggests.

## The Database Wasn't Deleted by a Rogue AI

The framing in the press cycle — *AI could delete everything in 9 seconds* — implies a system that went off-script. An AI that decided to do something it wasn't supposed to do. That is a more comforting narrative than the actual one.

The more likely story: an AI agent had permissions it shouldn't have had. It used those permissions to execute a task it was configured to execute. The deletion took nine seconds because the task completed efficiently. There was no adversarial behavior, no model failure, no hallucination. There was a gap between what someone thought the agent could access and what it actually could access — and that gap was never examined.

That distinction matters because it points to where the real work has to happen. The kill switch that ServiceNow is selling is useful. [The Register's coverage of the announcement](https://www.theregister.com/software/2026/05/05/servicenow-adds-agent-kill-switches-to-ai-control-tower/5228579) notes the discovery layer surfaces agents and MCP servers running across 30+ platforms — AWS, Azure, Google, Anthropic, OpenAI, all of it. If you don't know an agent is running, you cannot govern it.

But a kill switch only fires when someone recognizes that an agent is behaving badly. If the deletion looked, from the outside, like a database maintenance task completing normally — if the permissions were technically valid even though they shouldn't have been — the kill switch doesn't help. The damage lands before anyone pulls the lever.

## The Permissions Problem Isn't Solvable at Runtime

The nine-second incident is a permissions misconfiguration story. An agent had elevated access that enabled a destructive operation the operator did not intend to authorize.

How did it get those permissions? Almost certainly: the agent was deployed, credentials were configured, access was granted at integration time, and nobody characterized what that access actually enabled. This is the operational pattern that the current agent deployment cycle has made the default. Teams move fast. Agents get connected to systems. The permissions required for the happy path get provisioned. The permissions that come along for the ride — the ones that extend beyond the happy path — go unexamined.

[ServiceNow's expanded AI Control Tower](https://newsroom.servicenow.com/press-releases/details/2026/ServiceNow-expands-AI-Control-Tower-to-discover-observe-govern-secure-and-measure-AI-deployed-across-any-system-in-the-enterprise/default.aspx) addresses the visibility problem. You can catalog agents. You can observe what they're doing. You can kill them when something goes wrong. What it doesn't address — and what catalog-and-kill cannot address — is the question that has to be answered *before* an agent gets credentials: *what will this agent actually do with the access you're about to give it?*

That question isn't answerable from a catalog. It requires evaluation: running the agent against the task distribution it will face in production, including the edge cases where elevated permissions create unexpected blast radius. An agent configured to send emails shouldn't be able to delete the mailing list. An agent configured to query a database shouldn't be able to drop tables. These aren't exotic configurations — they are the gaps that open up between "the agent needs access to this system" and "we have characterized what operations the agent will perform under every realistic scenario."

## 60% Deploy, 10% Verify

The [2026 State of AI Agents report](https://www.arcade.dev/blog/5-takeaways-2026-state-of-ai-agents-claude/) contains a number that doesn't get enough attention: 60% of companies have started deploying agentic AI, but only one in ten has built anything genuinely autonomous. The gap isn't capability — it's confidence. Organizations are proceeding cautiously because they don't have a reliable way to know what their agents will do once they're running with real credentials against real systems.

The nine-second database deletion is the consequence of proceeding *un*cautiously. It's what happens when an organization closes that confidence gap with assumption rather than evidence.

The sequence that led to the incident: agent deployed, credentials provisioned, task executed, damage done. Each step followed naturally from the previous one because nobody introduced a verification checkpoint between "we're giving this agent access" and "the agent is running in production."

This pattern is not isolated. [Cognizant's research shows that 57% of organizations already deploy multi-step agent workflows](https://news.cognizant.com/2026-05-07-Cognizant-Launches-Secure-AI-Services-to-Help-Enterprises-Safely-Scale-Agentic-Systems), and 81% plan to expand into more complex use cases in 2026. Most of those deployments will follow the same sequence — access provisioned, verification skipped — because the tooling for pre-deployment verification hasn't been part of the standard deployment workflow.

## The Kill Switch Is the Last Line of Defense

The ServiceNow kill switch, offered free at a stated $2 million value, is the industry's best current answer to a problem that governance infrastructure can see but cannot prevent. It's a useful answer. It will stop incidents — if they take long enough for a human to notice and respond. For a nine-second deletion, that's a structural race condition, not a governance success.

The organizations that don't end up using a kill switch in emergency conditions are the ones that answer a harder question before deployment: not "does this agent have access to the systems it needs" but "have we characterized what this agent will do with that access."

That characterization is evaluation work. It means testing against the task distribution you actually care about, including adversarial inputs and edge-case configurations that never appear in the demo. It means understanding the agent's behavior when it has more authority than it strictly needs for the current task. It means catching the permissions gap before the agent runs, not after the damage is done.

The governance layer the industry is building is real and necessary. Discovery, observability, kill switches — these are infrastructure the enterprise agent ecosystem genuinely needs, and [ServiceNow's bet](https://www.techzine.eu/blogs/analytics/141044/servicenow-moves-beyond-control-tower-to-govern-and-kill-enterprise-ai/) is that this becomes foundational, not optional. But they operate at the wrong end of the problem. The governance gap shows up in production because the verification gap was never closed before deployment.

A kill switch is a last line of defense. It works considerably better when it is not the only one.
